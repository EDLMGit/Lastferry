# ANDROID_PLAYTEST_01 · Install Last Ferry on Android

Deliver a debug APK that a tester can install, switch into airplane mode and open for the first time. The complete twelve-cove Journey, thirteen Practice crossings, nine scored coves, supper and credits should work from that first launch. Start with game `000a1d51bdd5655448471a48d4f88d57a8b7f7b3` and current branch guidance. The existing web release must still build and play.

**Package the game.** Build the existing Vite/Three.js app and bundle its production output, including lazy assets and audio. A small Android WebView using AndroidX WebViewAssetLoader is a good fit for the relative asset paths. A locally bundled Capacitor shell is also viable. Codex owns the choice, supported Android/WebView versions and build tooling. Use one stable local HTTPS origin with JavaScript, DOM storage and accelerated graphics. The installed game must work without the private Site, sign-in, a development server or a first online visit. Keep the wrapper’s permissions and dependencies proportionate. [Android local content](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content) · [Capacitor workflow](https://capacitorjs.com/docs/getting-started)

**Keep the captain’s progress.** The app starts with its own saves. The browser playtest keeps its separate history. Keep the shell’s application ID, signing identity and web origin stable through playtest updates. Prove an in-place update with two progressively versioned debug builds and the same local signer. Keep an earned best, preferences and a Journey checkpoint through that update and a cold relaunch. Preserve original-byte backups when present and the existing cove-boundary restart contract. [Android update requirements](https://developer.android.com/google/play/app-updates)

**Play the installed build.** Use an Android emulator or available physical phone. Test offline first boot, a real rescue including Undo and arrival, and a late Journey handoff into supper and credits. Identify any prepared checkpoint. Exercise Android Back, rotation, gesture insets, system bars, background/resume, process death, sound and Reduced Motion. During ordinary rotation or a brief app switch the crossing should remain playable without extra turns, duplicate cues or lost choices. Give a usable explanation and recovery if the WebView cannot render the game. Examine touch responsiveness, visible water and companions, and audio on the tested setup. Label physical handling, performance and speaker checks still awaiting a handset.

**Hand back an installable build.** Supply the APK via the existing private handoff, SHA-256, tested source commit, reproducible build/install/update steps, Android/WebView version and concise device evidence. Use a provisional playtest application ID and standard local debug signing. The owner can choose the permanent Play identity, account and release-signing arrangements when preparing distribution. Keep signing keys private.

Verify that the same project can generate a test Android App Bundle with Android 16 (API 36) or higher as its target. Validate the bundle locally. The installable APK is the deliverable for this round. Permanent package registration, release credentials and Play Console submission belong to the owner in the next phase.
